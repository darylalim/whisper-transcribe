# Layout history

How the button right edges have been paired, kept so the history is not re-derived. It carries the current numbers (1102 / 1813) as well as the superseded ones; `CLAUDE.md` holds the same current numbers and is the copy to update, this file records how they got there. The live rules — re-measure after any change that adds or removes a bordered wrapper, the browser one-liner that does it, and never passing `wrap=` — stay in `CLAUDE.md` under **Input Modes**, in the standalone paragraph two below the `BUTTON_WIDTH = 168` bullet, which is also where the pointer here lives. Since the second move out of `CLAUDE.md` (the one forced by size; see the `docs/*.md` bullet under **Architecture**) the file also records the deleted label-left/control-right grid — `_control_row()`, `_labeled_toggle` and `_field_label` — the bordered controls card the settings lived in before the sidebar, the `SELECT_WIDTH` era of the button constant, and the pre-split / pre-theme measurements: the split's end-to-end run in Chrome, the single-column `wrap=` re-measurement at 1.63.0, and the borderless stock dropzone's truncation thresholds. All of it moved out of `CLAUDE.md` so it is read on demand rather than loaded into every session. The live rules stay there: **Input Modes** holds the sidebar bullet, the `st.columns(2, gap="small")` split, the `Advanced options`, `Transcript format`, **Time range** and `BUTTON_WIDTH` bullets and the card-inset rule, and **Accepted formats** holds the current ~1460 / ~1160 px thresholds; the split, `Advanced options`, `Transcript format`, **Time range** and no-grid bullets, the card-inset rule, the pairing paragraph, the `st.columns` bullet and the **Accepted formats** paragraph each carry a pointer back here (the sidebar bullet and the `BUTTON_WIDTH` bullet do not — nothing moved here from the first, and the second's `SELECT_WIDTH` sentence was condensed in place, with the pointer for it two paragraphs below in the pairing paragraph), and every section below opens by naming the bullet it came from so the two files cross-reference each other. Read it before restating the pairing, before re-deriving why a control took the form it did in the grid or why the expander sat inside the card, and before re-measuring the dropzone hint against the stock (borderless) dropzone. Sections run in `CLAUDE.md` order.

## Input Modes: the `Advanced options` expander inside the controls card

From the **Input Modes** bullet **The `Advanced options` expander is the sidebar's third tier, after the second `st.space`** — why the expander used to sit *inside* the controls card, and what the two bordered boxes looked like unnested. It used to be nested *inside* the controls card, and both halves of that were deliberate: semantically it is the third member of the input → output → advanced group, not a peer of it, and visually leaving it outside the card put two identically-bordered boxes a few px apart, so the card read as though it had been cut in half, while inset by the card's padding it read as subordinate (verified by rendering both). The card went with the move to the sidebar, so the visual half no longer applies — there is no border for the expander to fight — and the semantic half is carried by position and the seam alone.

## Input Modes: `Transcript format` in the main-column grid

From the **Input Modes** bullet **`Transcript format` is an `st.segmented_control`, and was an `Include subtitles` toggle**, whose pointer says how it sat in the deleted main-column grid is here. The control is the `st.segmented_control` that defaults to `width="content"` and measures 173 px for its two labels — the width that later ruled the grid out of the sidebar (the 314 px measurement is in the `st.sidebar` bullet of **Input Modes**). In the main-column grid it was the one right-hand control that did not take `width=SELECT_WIDTH` — pinning it to 168 would have clipped rather than aligned — and `_control_row()`'s `distribute` right-aligned it to the selectbox's edge (936 at a 1200 px viewport) instead; that grid held side-by-side from 1200 down to 420 px, and none of it survives the move.

## Input Modes: **Time range** as an inline `_control_row()`

From the **Input Modes** bullet **Time range is a native stacked `st.text_input` in the sidebar's Advanced options expander, carrying its own `help=`** — the input's life as an inline row in the main column, and the `_field_label` helper it was the exception to. It used to be an inline `_control_row()` at `width=SELECT_WIDTH` in the main column, matching the toggle above it and the four rows in the controls card, which left **Keyterms** as the app's only stacked control; now every control is stacked. The placeholder had been cut from `e.g., 30,90 (leave blank for full file)` to `e.g., 30,90` to fit 168 px, and stays cut: the input is 220 px wide in the expander and the dropped sentence lives in the `help` tooltip, which is the widget's own again. `_field_label`, which this row was the exception to, is deleted along with `_control_row` and `_labeled_toggle`.

## Input Modes: the label-left/control-right grid and its helpers

From the **Input Modes** bullet **There is no labelled-control grid any more, and no helper for one** — what `_control_row()` and its two wrappers were. `_control_row()` — `st.container(horizontal=True, horizontal_alignment="distribute", vertical_alignment="center")`, label first via `st.markdown(label, help=...)`, control second with `label_visibility="collapsed"` — and its two wrappers `_labeled_toggle(label, help_text)` and `_field_label(label, help_text)` are deleted. The rule used to be the inverse of what the sidebar does — **never a bare `st.toggle`**, help text on the label markdown rather than the widget's own `help=`, `width=SELECT_WIDTH` on the **Primary language** selectbox and the **Time range** input so the control half matched the toggles' right edge — because the grid needed the label and the control as separate children of one horizontal container. The reason the grid used a horizontal container rather than `st.columns([3, 1])` — and the A/B measurement behind it (`st.columns([3, 1])` broke between 800 px and 640 px while `_control_row()` stayed side-by-side down to 420 px) — is still live in `CLAUDE.md`, in the parenthesised bullet directly under this one, because a horizontal container remains the right construct for a *row*.

## Input Modes: `SELECT_WIDTH`, the constant `BUTTON_WIDTH` used to be

From the **Input Modes** bullet **`BUTTON_WIDTH = 168` is the width of the Transcribe and Download buttons, and of nothing else**. **It was `SELECT_WIDTH`**, and existed because `st.selectbox` has no `width="content"` — its default is `"stretch"`, which fills the whole horizontal container — with the **Time range** input and the two buttons taking the same constant so all four matched; the selectbox and the input no longer take a width at all, so the constant is named for what still does. The where-the-168-comes-from mechanism (`st.columns([3, 1])` in the `centered` layout, a 16 px gap and `calc(share − 16px)` flex bases, not "704 less a 32 px gap, over four") stays in that `CLAUDE.md` bullet, since it is what the constant still means.

## Input Modes: the controls card and the edge the buttons used to share

From the standalone **Input Modes** paragraph **The split is exactly "inside a bordered card" versus "not", and that is the whole rule** — the selectbox and the controls card each button used to pair with. The selectbox that used to share Download's inset from inside the controls card is in the sidebar now, and the controls card whose right border Transcribe used to line up with is gone — the two buttons are in different columns and have no edge to share. For the record, the pre-split statement of the same rule, as the `CLAUDE.md` of `e0df0a8` (the last commit before the sidebar landed in `ee40f33`) put it: "The selectbox sits in the controls card and Download sits in `_display_transcription`'s results card, so both inset by 16 px. Transcribe sits outside both and stays flush with the 704 px content edge — which is also where the controls card's own right border falls, so the button lines up with the **card** above it rather than with the selectbox inside it."

## The button right edges

The "original stale claim" the paragraph below refers to is the `BUTTON_WIDTH` bullet's — that the two buttons shared a right *edge* rather than a width; the bullet in `CLAUDE.md` still says an earlier version of it did. When the pairing changes again, append the new state here and bump the count in the `CLAUDE.md` pointer, rather than rewriting the paragraph.

Note the pairing has now changed three times, which is why the measurement is restated rather than reasoned about. It was selectbox+Transcribe at 952 with Download alone at 936; then selectbox+Download at 936 with Transcribe alone at 952; now there is no pairing at all — Transcribe alone at 1102 (1096.5 with a result on screen) in the input column and Download alone at 1813 in the results column, with the selectbox in the sidebar. (And the source comment's "they never did share a right edge" was false history in its first draft: before `aae209d` both buttons sat in `_, col = st.columns([3, 1])` with `width="stretch"` and no card existed, so both landed at 952; they stopped sharing an edge when that commit put Download inside the results card.) The original stale claim was written in `8b165dd` and invalidated by `aae209d`, the very next commit, which introduced the results container and simultaneously moved Download off `st.columns([3, 1])` + `width="stretch"` (which genuinely did yield `right=952`) onto `width=SELECT_WIDTH`.

## Input Modes: the pre-split `wrap=` re-measurement at 1.63.0

From the same standalone **Input Modes** paragraph as the pairing above — the one beginning **The pairing has changed three times** — whose `wrap=` sentence now says only "re-measured at 1.63.0" and points here for the pre-split figures. The full pre-split finding: `wrap=` and its default `None` changed nothing in this app — re-measured at 1.63.0 before the split, every rect of the single-column layout was within 0.4 px and all four grid rows held side-by-side at every viewport width listed. The widths "listed" were the eight in the pre-sidebar **Screenshots** section of `CLAUDE.md`, which `ee40f33` removed along with the single-column layout; recovered from `e0df0a8`, that section read: "All four labelled rows still hold side-by-side at 1200 / 900 / 800 / 700 / 640 / 520 / 460 / 420 px, and the selectbox and Transcribe stay exactly 168 px wide at every one of them." The "four grid rows" are the four `_control_row()` rows in the controls card — **Primary language**, **Translate to English**, **Transcript format** and **No verbatim** — which is the grid the section above describes.

## Input Modes: the earlier claim for `st.columns([3, 1])` on the button rows

From the **Input Modes** bullet **The only `st.columns` in `streamlit_app.py` is the module-level `input_col, results_col = st.columns(2, gap="small")` that splits the main area**, whose pointer says this file has the earlier claim. "This file", in the sentence as it was written, is `CLAUDE.md`. An earlier version of this file justified keeping `st.columns([3, 1])` on the two button rows with "(a button *does* need a width ratio)". That was false when written: `st.button` and `st.download_button` both accept `width` as an int pixel value, in the locked 1.63.0 *and* well below the declared `>=1.59` floor.

## Accepted formats: the pre-theme stock dropzone thresholds

From the **Accepted formats** paragraph **The `wide` layout puts the uploader in the left of two equal `st.columns(2, gap="small")`**, whose pointer promises the pre-theme stock figures, why the border shifts them by 4px rather than 2, and the README rounding that absorbed it. The current thresholds are ~1460 px with the sidebar open and ~1160 px with it collapsed (fits at 1459 / 1159, truncates at 1458 / 1158), measured under the theme's 1px `showWidgetBorder` edge on the dropzone. The borderless stock dropzone fit down to 1456 / 1156, and the 4px is the theme's 1px border on each side of the dropzone, doubled across two equal columns; the README already rounded both figures to "about 1460" and "about 1160", so its numbers did not move. The format list's budget inside the 722 px input column at 1920 moved the same way: ~497px before the border (589 px slot less the 92 px size prefix), ~495px under it (587 − 92) — the figure `test_format_list_fits_the_dropzone_hint`'s description in **Testing** used to restate, and now leaves to **Accepted formats**. Which of the two figures a re-measurement lands on is decided by the `.streamlit/config.toml` precedence trap in `docs/screenshots.md` — a scratch-directory harness that does not copy the repo's config beside the script measures the stock dropzone, not the themed one.
