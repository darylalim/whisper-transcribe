# Screenshot capture recipe

How `docs/screenshot.png` and `docs/screenshot-result.png` are produced. Moved out of `CLAUDE.md` so it is read when the assets are reshot rather than loaded into every session. In `CLAUDE.md`, the `docs/screenshot.png` bullet under **Architecture** carries the rule for *when* to reshoot, and the **Screenshots** section keeps the dimensions (restated in the intro below and in the anchor bullet's `(494)` / `(805)`; update all three), the read trigger and the two measurement keys (the sidebar's width in Chrome versus headless Playwright, and px layout versus rem type).

`docs/screenshot.png` / `docs/screenshot-result.png` are **1600 px wide** (1600×494 and 1600×805) and script-captured rather than hand-shot, so the pair stays mutually consistent. They were 896 px wide while the app was a single `centered` column; the sidebar + two-column layout has no 736 px block to clip to, so the frame is now the **whole viewport**, from the sidebar's left edge to the main area's right padding, at one output px per CSS px. The recipe, in case it needs re-deriving:

- **Playwright driving the installed Chrome** — `uv run --no-project --with playwright --with pillow`, then `p.chromium.launch(channel="chrome", headless=True)`. The default `chromium` launch fails asking for `playwright install` (the cached build predates the current release); `channel="chrome"` needs no download. The two obvious alternatives are both dead ends: `screencapture` needs a Screen Recording grant, and the Chrome MCP `computer` tool returns a downscaled JPEG — wrong for a PNG asset
- **Geometry**: viewport **1600×1000**, `device_scale_factor=2`, `color_scheme="dark"`. Clip `x=0, y=0, width=1600, height = max(sidebar expander bottom, Transcribe bottom, Download bottom) + 32`, then downscale the 2× capture by exactly half (Lanczos) to 1600 wide — the 2× buys anti-aliasing, not reframing. No horizontal pad and no `.stMainBlockContainer` arithmetic: the sidebar starts at `x=0` and the main block's own 80 px side padding is the right margin. At 1600 the block is `x=300, w=1300` with 96 px of top padding and 80 px each side (160 px at the bottom), so the content box is `x=380..1520` and the two columns are **562 px** each at `x=380` and `x=958` with the 16 px `gap="small"` between them (722 px each at the user's 1920). The centered recipe clipped the 736 px padding box plus ~3% per side — `x = 232 − 0.03×736`, `width = 736 × 1.06 = 780`, downscaled to 896 from a 1560 px capture, and 736 was the *padding* box where 704 was the content box — none of which applies with the settings in a 300 px sidebar
- **1600 rather than the display's 1920 is measured, not taste.** GitHub shows a README image at ~900 px regardless of its size, so a 1920 asset only buys tinier text; and the width cannot go much lower because the input column shrinks with the viewport and the dropzone hint truncates once its span drops under the hint text's **357 px** natural width (14 px Source Sans, `500MB per file • MP3, …, MKV`, the same 92 + ~265 the **Accepted formats** section of `CLAUDE.md` describes). With the sidebar open the slot the span sits in (`stFileUploaderDropzoneInstructions`, which is what the `startsWith('500MB')` lookup in the capture script returns) is 587 px at 1920, 427 at 1600, 357 at 1460 and 356 at 1458 under the theme's 1 px dropzone border (589 / 429 / 1456 / 1454 for the borderless stock dropzone) — the 14 px span itself stays at its 357 px natural width until the slot drops under it — so the floor is ~1460 px and 1600 is the first round width with real margin
- **Anchor the clip's bottom, not its top.** `y=0` is correct now — the sidebar runs from the top of the viewport and its `Settings` heading (`y=76`) sits in the same band as the `h1` (`y=96`), so the ~96 px of `padding-top` the centered recipe cropped away by anchoring on `main.querySelector('h1')` is part of the frame; an `h1`-anchored top would slice the sidebar mid-gutter. The bottom is the lowest of three anchors plus a flat 32 px pad, and a different one wins per asset: in the input state the sidebar's **Advanced options** expander bottoms at `461.6`, under Transcribe (`403.2`), so the **sidebar** sets the height (494); in the result state **Download** bottoms at `772.8`, so the results card does (805). The pad clears the results card's bottom border, which sits 16 px below Download (`788.8`) — bound on the button, not on the card, since `st.download_button` is the first element with a border of its own and there is no settings card to mis-anchor on any more. The two assets are deliberately *not* the same height, only the same width, as the old 896×783 / 896×596 pair was not either
- **The harness runs from a scratch directory, and the script-level `.streamlit/config.toml` wins over the project's** (`get_config_files` appends the config beside the main script last, so it overrides `$CWD/.streamlit/config.toml`; same at 1.59.0). Copy the repo's `.streamlit/config.toml` beside the harness before capturing, or every shot ships Streamlit's stock red — the first theme-comparison renders in this repo did exactly that until the copy was added. `color_scheme="dark"` is what selects the `[theme.dark]` variant; the same harness with `"light"` renders the sibling, which is how the light mode was reviewed even though no light screenshot is checked in
- **`docs/screenshot-result.png` needs a post-transcription state, and no `sample.wav` is checked in.** Drive a scratch harness that seeds `st.session_state["transcription"]` / `["batch_id"]` and then `exec`s the app source with two textual injections. The first is unchanged in spirit: `status_slot.status("Transcribed 1/1 file", expanded=False, state="complete")` immediately above the `if st.session_state.get("transcription"):` that guards the `st.fragment(_display_transcription)()` call — **at that line's four-space indent**, since it sits inside `with results_col:` and an unindented injection is an `IndentationError`; a needle on the fragment call itself, which is nested one level deeper now, lands the status at the wrong indent and is a `SyntaxError` — **on `status_slot`, not `st`**, because the real status renders inside the reserved slot the results column opens first (`status_slot = st.container()`; the `st.columns(2, gap="small")` bullet under **Input Modes** in `CLAUDE.md`, and the source comment above it) and a bare `st.status` would land after it — visually identical, since an empty slot renders no node, but not the app's own tree — and **that string has to track `_handle_transcription`'s real label**, built from `_plural` (a harness left on the old `file(s)` silently ships a label the app no longer produces). The seeded transcription dict needs the `transcript` key `_display_transcription` reads (the rendered text; `_handle_transcription` computes it at publish time). The second is new to the side-by-side frame: `uploaded_files = uploaded_files or _seed_upload()` immediately after the `st.file_uploader(...)` call, with `_seed_upload` returning a fresh `UploadedFile` over a real short MP3 (`say -o clip.aiff "…"` + `ffmpeg` makes one in a second) — a fresh object per call, as the real widget deep-copies per run. The old recipe cropped the input area out of the result shot entirely, which a two-column layout cannot do, and without the seed the frame shows an empty dropzone and a *disabled* Transcribe next to `Transcribed 1/1 file`. **Inject after the call; do not `patch("streamlit.file_uploader")`.** A patched widget never renders, so the dropzone itself vanishes from the input column (the first attempt shipped exactly that). Injected, the dropzone renders, the `st.audio` preview appears under it and Transcribe enables; the dropzone's file chip is frontend state that Python cannot seed and is the one thing the result shot lacks. The preview also moves Transcribe: its bottom is `403.2` with nothing loaded and `459.2` with the player above it
- **Wait for the layout to settle before capturing.** The audio element's load transiently shifts the Transcribe button to the *left* edge of its column, and a capture taken a fixed 2 s after load shipped it left-aligned while the live tab showed it flush right (`justify-content: end` on the horizontal block, verified in the DOM). Poll until the button's `right` equals the input column's `right` (942 at 1600) and `[data-testid="stStatusWidget"]` is gone, and fail loudly if it never does
- **Anchoring: two selectors bite.** `st.status` and `st.expander` share `data-testid="stExpander"`, and the result harness has both on the page — the **Advanced options** expander in the sidebar and the `Transcribed 1/1 file` status in the results column. The expander is the anchor and the status is not, so scope the lookup to the sidebar: `[data-testid="stSidebar"] [data-testid="stExpander"]`. A bare `querySelector` happens to return the sidebar's because the sidebar precedes the main block in the DOM, but the scope is what stops that depending on order. Second: **`innerText.includes('Transcribe')` also matches `Transcribed 1/1 file`**, so the lookups for the Transcribe and Download buttons need `&& !b.innerText.includes('Transcribed')` — the substring trap only exists in the result harness, where both strings are on the page at once. The status-anchored top and its clamp against Transcribe's bottom went with the stacked layout: the status renders beside the button, not under it
- Hide `[data-testid="stToolbar"]`: the Deploy button and hamburger are browser chrome, not app UI
- The `st.logo(":material/graphic_eq:", size="small")` mark renders in the sidebar header at `x=31, y=20`, 20×20 (`data-testid="stSidebarLogo"`), inside the fixed header row, so `Settings` stays at `y=76` and no anchor moves; it is in both frames. It is not in `AppTest`'s element tree (the logo `ForwardMsg` carries no `delta` and is dropped), so `test_logo_is_the_page_icon_glyph` pins the call by patching `streamlit.logo`; the screenshots are the only record of how it *renders*. The per-result heading's `:material/description:` prefix is likewise in the result frame, and it changes the heading's auto-anchor from `#interview-mp3` to `#description-interview-mp3` (nothing links to either)
