# CLAUDE.md

Streamlit application for transcription and translation using OpenAI Whisper on Apple Silicon with MLX.

## Setup

```bash
uv sync
uv run streamlit run streamlit_app.py
```

Python floor is **3.12** (`requires-python`), and `[tool.ty.environment] python-version = "3.12"` pins `ty` to it — so a 3.13-only stdlib symbol runs fine in the local 3.13 `.venv`, passes `pytest`, and fails `ty check` with an error pointing at `pyproject.toml`. There is no `.python-version`, so a fresh `uv sync` takes the newest interpreter uv can find that satisfies the floor, managed installs first — **3.14** on this machine at the time of writing, while the checked-in `.venv` was created on 3.13.12 and is what every `uv run` inside the repo still uses (`uv sync` reuses an environment whose interpreter still satisfies `requires-python`). So a fresh clone can land on a different minor than the existing venv; every "3.13" in this file describes that venv, not a property of the setup. CI pins `UV_PYTHON: "3.12"` instead, so the floor is exercised there and only there.

## Commands

- **Lint**: `uv run ruff check .`
- **Format**: `uv run ruff format .`
- **Typecheck**: `uv run ty check`
- **Test**: `uv run pytest`

When working with Python, invoke the relevant `/astral:<skill>` for uv, ty, and ruff to ensure best practices are followed.

When changing the Streamlit UI (tabs, widgets, theme, layout, caching, fragments), invoke the `developing-with-streamlit` skill to stay version-correct against the locked Streamlit version (currently 1.63.0; the floor is `>=1.59`). ⚠️ **The references it loads are not the skill's own — they ship inside the installed Streamlit wheel (`streamlit/.agents/skills/developing-with-streamlit/`), so they describe the *installed* version, never the floor.** The user-level skill is only a `discover.py` that resolves that path from the project's `.venv` (`$VIRTUAL_ENV` wins if set, so an unrelated activated venv loads *its* Streamlit's docs), which means every upgrade silently swaps the guidance. It once recommended `st.skeleton` against the old `>=1.58` floor; the 1.63.0 references recommend, without any version qualifier, `st.title/header/subheader(icon=)`, `@st.fragment(key=)` + `st.rerun("<key>")`, `st.status`/`st.expander(type="step")` and `runner.cacheBackgroundRefreshTTLMultiplier` (all 1.63.0-only), `wrap=` on containers/columns/buttons/toggles/multiselect (1.62.0) and on `st.segmented_control`/`st.markdown` (1.63.0), `refresh_mode="background"` (1.61.0), and `from streamlit.typing import UploadedFile` (1.62.0) — none of which exist at the floor, and nothing in the gate would notice, since the `Stop` hook runs the local `.venv` and CI runs `uv sync --locked`, both 1.63.0. The `streamlit.typing` one is an instruction, not a suggestion: the 1.63.0 `SKILL.md` and `api-reference.md` say to import `UploadedFile` from it and "not from modules under `streamlit.runtime`". `streamlit_app.py` and `tests/test_app.py` deliberately keep `streamlit.runtime.uploaded_file_manager` — the module is a `ModuleNotFoundError` at 1.59–1.61, the class is the same object either way, and `UploadedFileRec`, which the tests need, is not re-exported from it. Check any newly-recommended API — *parameters included*, since `hasattr` is satisfied by a command that exists but lacks the recommended kwarg — against the floor before using it: `uv run --no-project --with 'streamlit==1.59.0' python -c "import inspect, streamlit as st; print(inspect.signature(st.<name>).parameters)"` settles it in one command. Raise the floor deliberately rather than by accident.

## Automation

- **Hooks** (`.claude/settings.json`, checked in): a `PostToolUse` hook runs `ruff format` + `ruff check --fix` on edited `*.py` files and `ruff format` alone on edited `*.md` files (`ruff check` is a no-op on Markdown — it reports "No Python files found" and exits 0, so only the formatter is worth running there) — both branches sit behind a `case "$f" in "$PWD"/*)` containment guard, since the hook fires on *any* edit Claude makes and `cd "$CLAUDE_PROJECT_DIR"` pins only ruff's **config** discovery, not its **target**: without the guard an edit to `~/.claude/**` or a scratchpad file is reformatted with this project's `line-length = 100`; a `Stop` hook gates on `uv lock --check` + `ruff check` + `ruff format --check` + `ty check` + `pytest`, feeding failures back for repair (guarded against re-engage loops via `stop_hook_active`, and entered via `cd "${CLAUDE_PROJECT_DIR:-.}"` so an unset variable falls back to the cwd rather than `cd ""`-ing into a silent `exit 0` that skips the whole gate). Personal overrides live in the gitignored `.claude/settings.local.json`
- **The Stop hook deliberately duplicates the `PostToolUse` hook's `ruff` work.** `PostToolUse` ends in `> /dev/null 2>&1 || true`, so if `uv run ruff` ever breaks (venv rebuilt, `$CLAUDE_PROJECT_DIR` unset, or a path that the containment guard rejects) it silently stops formatting with no signal. Running `ruff` in the `Stop` gate too costs ~50 ms (measured: ~4.3 s for the full gate vs. ~4.3 s for `ty` + `pytest` alone — indistinguishable within run-to-run noise, with `pytest` ~4.0 s of it) and converts that silent failure into a blocking one. Do not "de-duplicate" it
- The two `ruff` steps in the `Stop` hook take `-q`; `ty check` deliberately does **not**. `ruff -q` suppresses only the success chatter and still prints full diagnostics on failure, but `ty check -q` collapses a real type error to the bare line `Found 1 diagnostic` — which, as the `reason` fed back for repair, names neither the file nor the problem. `ty check` also exits 1 on any `warn`-level diagnostic, not only errors (`--exit-zero-on-warning` is the opt-out, and the gate passes neither it nor `--error-on-warning`), so a warning blocks the `Stop` hook and CI exactly like an error — that is what turned the stale `ty: ignore` on `import mlx.core` into a red gate the moment the lock moved to an mlx release that ships stubs (see **Model**). Of the ten rules added between ty 0.0.69 and 0.0.80, three are on by default: `invalid-module-getattr-call` (error), `missing-slot` (error) and `redundant-condition` (warn); the last is the only one with a realistic surface here — an `if` whose operand is statically always truthy, e.g. a forgotten `()` on a function name
- **CI** (`.github/workflows/ci.yml`): runs `ruff check` + `ruff format --check` + `ty check` + `pytest` on push to `main` and on PRs. Pinned to a **`macos-14` (Apple Silicon) runner**, and the job sets `UV_PYTHON: "3.12"` — the only place the declared floor is actually exercised, since the local `.venv` runs 3.13. There is no `uv python install` step: `uv sync --locked` provisions the interpreter, and a bare `uv python install` would fetch uv's newest default instead of the pin. `enable-cache: true` on `setup-uv` is load-bearing rather than cosmetic — `mlx-whisper` depends on **`torch`**, ~520 MB installed at 2.14.0 (apparent size of `site-packages/torch` with `__pycache__` excluded; `du -sh` reads 542M once bytecode is compiled; ~500 MB at 2.13.0), so a cold cache dominates the run. It is install cost only — `mlx_whisper/torch_whisper.py` is its sole user and nothing imports that module, so neither the app nor the tests ever load `torch`
- **Every action is pinned to a full commit SHA**, with the version in a trailing comment (`actions/checkout@3d3c42e… # v7.0.1`). Tags are mutable, so a `@v7` that is force-moved or compromised runs arbitrary code holding the workflow's token — and the `release` job below carries `contents: write`. Use a SHA for any action added later, and bump the trailing comment with it
- **Dependabot** (`.github/dependabot.yml`) keeps those pins from going stale — a frozen SHA never surfaces the security fix it is missing. Weekly `github-actions` updates only (**not** `uv`/Python deps), grouped into a single PR and prefixed `ci:` to match the commit convention. It rewrites the SHA *and* its trailing `# vX.Y.Z` comment together, which is the property that makes SHA pinning maintainable. `directory: "/"` is required for this ecosystem — Dependabot scans `.github/workflows` on its own and does not take that path. Version updates need no repo setting; the config file's presence on `main` is what enables them
- **`macos-14` is required by the backend, not by wheel availability** — the older "`mlx-whisper` ships no Linux wheels" rationale is obsolete. `mlx_whisper` is a pure-Python `py3-none-any` wheel and `mlx` ships `manylinux_2_35` wheels that are already in `uv.lock`, so `uv sync --locked` resolves *and installs* fine on Linux. But `mlx` depends on its compute backend unconditionally only on Darwin (`mlx-metal`); on Linux the backend is opt-in (`mlx-cpu` / `mlx-cuda-*`, gated behind the `cpu` / `cuda` extras) and the lockfile carries neither. A Linux runner therefore goes green through `uv sync` and dies at `import mlx_whisper` several steps later. Switching to `ubuntu-latest` is possible by adding `mlx[cpu]`, but it would test a backend the app never ships on
- **Release** is the `release` job *inside* `ci.yml` (there is no separate release workflow; `draft-release.yml` was merged in). It reads `project.version`, then tags the commit and **publishes** `v<version>` with auto-generated notes. Runs on plain `ubuntu-latest` (unlike `check`) because it never calls `uv sync`, so the Darwin-only `mlx` backend never has to install
- ⚠️ **Bumping `version` in `pyproject.toml` publishes a public GitHub Release** — it tags `main`, marks the release Latest, and notifies watchers. A publish is not cleanly reversible: deleting it leaves anyone who already fetched the tag on a version that no longer exists. An incidental bump in an unrelated `pyproject.toml` edit therefore ships a release, so treat `version` as the release trigger it is. To stage one for review instead, drop `--draft=false` from the `gh release edit` line and publish by hand
- The release job's guard is the **release's existence**, not a `paths:` filter — it runs on every push to `main` and no-ops when `v<version>` is already published. A `paths:` filter misses a bump that arrives inside a merge commit and cannot be re-run after a failure; the existence check is idempotent and re-runnable. It resolves three states: `published` → exit, `draft` → publish it (a previous run died between the two `gh` calls; skipping would strand that draft forever), `missing` → create the draft, then publish. Anything else fails loudly rather than publishing a release whose state is unknown
- **`needs: check` is the point of the merge.** As a standalone workflow the release ran independently of CI, so a version bump drafted a release even when `ruff`/`ty`/`pytest` were red. Nothing may publish ahead of a green `check`
- Two details in the release job that look incidental and are not: `permissions: contents: write` is set **per job**, so the write scope never reaches the `check` job that actually runs third-party code; and `cancel-in-progress` is `${{ github.event_name == 'pull_request' }}` rather than plain `true`, because a blanket cancel can kill a `main` run mid-publish, between creating the draft and flipping it live
- **Creating the release as a draft first is load-bearing, not ceremony.** GitHub withholds the git tag while a release is a draft and creates it on publish, so a failure during note generation leaves no tag pointing at an unreleased commit

**The `Stop` hook mirrors every CI step.** `uv lock --check` is what stands in for `uv sync --locked`: `uv.lock` pins the project's own version, so bumping `version` in `pyproject.toml` needs `uv lock` in the same commit or CI fails. That used to be the one failure with no local signal.

**`uv lock --check` must run *first*, ahead of every `uv run` step — the ordering is load-bearing, not cosmetic.** `uv run` syncs the project environment before running its command, which **rewrites `uv.lock` in place**. So the gate's own first `uv run ruff` silently repairs the drift, and a `uv lock --check` placed after it can never fail. Measured both ways: with the check third in the chain, a bumped `version` passed the gate green and left `uv.lock` dirty in the working tree; moved to first, it blocks with `The lockfile at 'uv.lock' needs to be updated`. The step costs ~0.02 s and the five-step gate measures ~4.3 s (`pytest` ~4.0 s, `ty` ~0.2 s, the three `uv`/`ruff` steps under 0.1 s combined). That is up from the 3.17–3.25 s first recorded at `51d935a`, because the suite grew from 55 to 101 test functions (181 cases) before the YouTube and URL tabs were removed — it was 89 functions (163 cases) after that, and is 100 functions (174 cases) since the sidebar + two-column layout landed, when the gate re-measured at 4.4 s with `pytest` ~3.9 s of it, and 105 functions (181 cases) with the theme cases, `pytest` ~3.8 s — not because of any dependency change. The same property is why the local drift is easy to miss in the first place — any stray `uv run` fixes the lockfile on disk without staging it.

The gate mirrors CI's **steps**, not its **interpreter**: the hook runs against the local `.venv` (3.13) while CI pins `UV_PYTHON: "3.12"`. So a 3.13-only stdlib symbol passes the `Stop` hook's `pytest` and fails CI's. `ty check` is what closes that gap locally — `[tool.ty.environment]` targets 3.12 no matter which interpreter is running it — which is a reason not to drop it from the gate on the grounds that `pytest` already exercises the code.

Two `ruff` behaviors the gate now covers, worth keeping in mind rather than rediscovering:

- `ruff format` covers **Markdown** (0.16 reformats Python inside fenced code blocks in `.md`), so CI's `ruff format --check .` gates `CLAUDE.md` and `README.md`, not just the two `.py` files — `ruff format --check .` reports **4 files**
- selecting all of `E` enables `E501`, so an over-long line is a `ruff check` **error**, not something the formatter rewraps. But `E501` exempts a line that is a single whitespace-free token — a 124-character `x='<120 chars>'` (no spaces around `=`, so one token) passes `ruff check`, and `ruff format --check` catches it only incidentally, by normalizing the spacing and quotes: the same literal on its own line as `"<122 chars>"` passes **both** tools, and `x = '<120 chars>'` — the example this line used to carry — is three tokens and *is* flagged (measured at ruff 0.16.2 and 0.16.7). The gate runs both because each catches what the other cannot, not because the formatter backstops the exemption

## Code Style

- snake_case for functions/variables, PascalCase for classes
- Type annotations on all parameters and returns in `streamlit_app.py`; `tests/test_app.py` is deliberately unannotated (fixtures and mocks) and no `ANN` rules are selected
- `RuntimeError` for known transcription failures (no custom exception class)
- Import sorting via ruff with combine-as-imports
- `line-length = 100` (ruff's default is 88), `select = ["E", "F", "I", "W"]`

## Commits

- **Conventional Commits, lowercase throughout, no trailing period.** Subjects are `type: summary` or `type(scope): summary` — `fix`, `feat`, `refactor`, `docs`, `test`, `style`, `perf`, `ci` and `chore` (with `chore(deps)` and `chore(hooks)` as the scopes in use) all appear in the log — with the summary in the imperative and, when a commit does two things, both named, joined by `, and` or `;` (`fix: rewind the recording, and collapse whitespace at the heading sink too`). Subjects run up to 80 characters. Bodies are prose paragraphs wrapped by hand under ~80 columns that state the claim or defect, the fix, and the measurement behind it — the same register as this file, since most of them end up quoted here
- **The history is linear, and `CLAUDE.md` travels in the same commit as the change it describes.** There are no merge commits; the only pull requests ever opened are Dependabot's (`#1`, `#2`), squash-merged with the `(#N)` suffix GitHub appends, and everything else is committed to `main` directly. Every code commit in the log also touches `CLAUDE.md`, and the "means a README edit in the same commit" rules under **Architecture** are the same practice for `README.md` — a doc update is part of the change, not a follow-up. The `ci:` prefix in `.github/dependabot.yml` is what keeps Dependabot's PRs in this shape

## Architecture

- `streamlit_app.py` — single-file app entry point
- `tests/test_app.py` — unit tests
- `README.md` — user-facing docs, and the repo's largest concentration of hand-duplicated facts. It restates the accepted-format list, the 500 MB per-file cap, the Python floor, the `macos-14`/`mlx`-backend CI rationale, `ASR_MODEL_REPO` and its ~1.5 GB first-run weight download, the four dev commands, the `.srt`/`.txt` download switch, the 42-character subtitle wrapping, every Advanced-options control's description, and — since the wide layout — where everything sits: that the settings live in a **Settings** sidebar with **Advanced options** at its bottom, that transcripts render beside the input, that an invalid time range is flagged beside **Transcribe**, the viewport thresholds at which the sidebar collapses (~770 px), the panels stack (640 px) and the dropzone's format list abbreviates (the README's "about 1460 px" with the sidebar open and "about 1160 px" collapsed, which rounded the measured 1456 / 1156 px of the borderless stock dropzone and are the exact figures under the theme's 1 px border), that the theme switch is in Streamlit's ⋮ menu and *not* in that sidebar, that the light and dark themes are macOS-styled (bullet 24, and both screenshots, which show the dark one), and (in the first screenshot's alt text) the empty-state hint `Transcripts appear here`. So changing `AUDIO_FORMATS`/`VIDEO_FORMATS`, `server.maxUploadSize`, `requires-python`, `runs-on`, `ASR_MODEL_REPO`, `PAGE_CONFIG["layout"]`, `EMPTY_RESULTS_HINT`, any control's label or `help` text, or which column, sidebar or container a control or alert renders in means a README edit in the same commit. Nothing checks this — the runner rationale drifted silently and took `53b1f8d` to correct
- `docs/screenshot.png`, `docs/screenshot-result.png` — embedded in README with descriptive alt text naming the Settings sidebar and its controls, the two input tabs, the input | results split and, in the empty state, the `Transcripts appear here` hint. Reshoot both, and update the alt text, on any UI or theme change; nothing checks them. See **Screenshots** below for the capture recipe

### Screenshots

`docs/screenshot.png` / `docs/screenshot-result.png` are **1600 px wide** (1600×494 and 1600×805) and script-captured rather than hand-shot, so the pair stays mutually consistent. They were 896 px wide while the app was a single `centered` column; the sidebar + two-column layout has no 736 px block to clip to, so the frame is now the **whole viewport**, from the sidebar's left edge to the main area's right padding, at one output px per CSS px. The recipe, in case it needs re-deriving:

- **Playwright driving the installed Chrome** — `uv run --no-project --with playwright --with pillow`, then `p.chromium.launch(channel="chrome", headless=True)`. The default `chromium` launch fails asking for `playwright install` (the cached build predates the current release); `channel="chrome"` needs no download. The two obvious alternatives are both dead ends: `screencapture` needs a Screen Recording grant, and the Chrome MCP `computer` tool returns a downscaled JPEG — wrong for a PNG asset
- **Geometry**: viewport **1600×1000**, `device_scale_factor=2`, `color_scheme="dark"`. Clip `x=0, y=0, width=1600, height = max(sidebar expander bottom, Transcribe bottom, Download bottom) + 32`, then downscale the 2× capture by exactly half (Lanczos) to 1600 wide — the 2× buys anti-aliasing, not reframing. No horizontal pad and no `.stMainBlockContainer` arithmetic: the sidebar starts at `x=0` and the main block's own 80 px side padding is the right margin. At 1600 the block is `x=300, w=1300` with 96 px of top padding and 80 px each side (160 px at the bottom), so the content box is `x=380..1520` and the two columns are **562 px** each at `x=380` and `x=958` with the 16 px `gap="small"` between them (722 px each at the user's 1920). The centered recipe clipped the 736 px padding box plus ~3% per side — `x = 232 − 0.03×736`, `width = 736 × 1.06 = 780`, downscaled to 896 from a 1560 px capture, and 736 was the *padding* box where 704 was the content box — none of which applies with the settings in a 300 px sidebar
- **1600 rather than the display's 1920 is measured, not taste.** GitHub shows a README image at ~900 px regardless of its size, so a 1920 asset only buys tinier text; and the width cannot go much lower because the input column shrinks with the viewport and the dropzone hint truncates once its span drops under the hint text's **357 px** natural width (14 px Source Sans, `500MB per file • MP3, …, MKV`, the same 92 + ~265 the **Accepted formats** budget describes). With the sidebar open the slot the span sits in (`stFileUploaderDropzoneInstructions`, which is what the `startsWith('500MB')` lookup in the capture script returns) is 587 px at 1920, 427 at 1600, 357 at 1460 and 356 at 1458 under the theme's 1 px dropzone border (589 / 429 / 1456 / 1454 for the borderless stock dropzone) — the 14 px span itself stays at its 357 px natural width until the slot drops under it — so the floor is ~1460 px and 1600 is the first round width with real margin
- **Anchor the clip's bottom, not its top.** `y=0` is correct now — the sidebar runs from the top of the viewport and its `Settings` heading (`y=76`) sits in the same band as the `h1` (`y=96`), so the ~96 px of `padding-top` the centered recipe cropped away by anchoring on `main.querySelector('h1')` is part of the frame; an `h1`-anchored top would slice the sidebar mid-gutter. The bottom is the lowest of three anchors plus a flat 32 px pad, and a different one wins per asset: in the input state the sidebar's **Advanced options** expander bottoms at `461.6`, under Transcribe (`403.2`), so the **sidebar** sets the height (494); in the result state **Download** bottoms at `772.8`, so the results card does (805). The pad clears the results card's bottom border, which sits 16 px below Download (`788.8`) — bound on the button, not on the card, since `st.download_button` is the first element with a border of its own and there is no settings card to mis-anchor on any more. The two assets are deliberately *not* the same height, only the same width, as the old 896×783 / 896×596 pair was not either
- **The harness runs from a scratch directory, and the script-level `.streamlit/config.toml` wins over the project's** (`get_config_files` appends the config beside the main script last, so it overrides `$CWD/.streamlit/config.toml`; same at 1.59.0). Copy the repo's `.streamlit/config.toml` beside the harness before capturing, or every shot ships Streamlit's stock red — the first theme-comparison renders in this repo did exactly that until the copy was added. `color_scheme="dark"` is what selects the `[theme.dark]` variant; the same harness with `"light"` renders the sibling, which is how the light mode was reviewed even though no light screenshot is checked in
- **`docs/screenshot-result.png` needs a post-transcription state, and no `sample.wav` is checked in.** Drive a scratch harness that seeds `st.session_state["transcription"]` / `["batch_id"]` and then `exec`s the app source with two textual injections. The first is unchanged in spirit: `st.status("Transcribed 1/1 file", expanded=False, state="complete")` immediately above the `if st.session_state.get("transcription"):` that guards the `st.fragment(_display_transcription)()` call — **at that line's four-space indent**, since it sits inside `with results_col:` and an unindented injection is an `IndentationError`; a needle on the fragment call itself, which is nested one level deeper now, lands the status at the wrong indent and is a `SyntaxError` — and **that string has to track `_handle_transcription`'s real label**, built from `_plural` (a harness left on the old `file(s)` silently ships a label the app no longer produces). The second is new to the side-by-side frame: `uploaded_files = uploaded_files or _seed_upload()` immediately after the `st.file_uploader(...)` call, with `_seed_upload` returning a fresh `UploadedFile` over a real short MP3 (`say -o clip.aiff "…"` + `ffmpeg` makes one in a second) — a fresh object per call, as the real widget deep-copies per run. ### Subtitle wrapping

`_format_srt` runs every cue through **`_wrap_cue`**, which wraps to `SUBTITLE_LINE_WIDTH = 42` — the broadcast convention (Netflix, BBC, EBU all land on 42 for Latin scripts). Whisper emits one segment per utterance with no regard for line length, so cues routinely ran well past it: valid SRT that every player accepts and that looks wrong burned into a picture. This is a **display** constraint, not a format one, which is why nothing but an explicit assertion catches a regression. Plain text is untouched.

Three details, each of which was wrong in a first draft:

- **Greedy wrapping alone is not enough.** `textwrap` fills each line to the brim and leaves a one-word orphan — more conspicuous on screen than the long line it replaced. `_wrap_cue` re-wraps at the *narrowest* width still producing the same line count, which spreads words evenly
- **`break_long_words=False` does not stop hyphen splitting.** `textwrap.break_on_hyphens` defaults to `True` and cut `https://example.com/an-extremely-long-path` in half mid-URL. Both flags are off, so the rule is simply "never split a token": an over-long token overflows its line instead
- ⚠️ **Do not add a "never narrow below the longest token" floor.** It looks obviously right and is measurably wrong — over 39k generated cues it changed 74, and *every* change was less balanced (`[24,24,22,21,30]` → `[24,24,29,14,30]`), while the over-long-token case it was meant to fix comes out byte-identical either way, because a token wider than `width` lands on its own line at every candidate width. The comment in the source records this so it does not get re-derived

The leading `" ".join(text.split())` is structural, not tidiness: a newline inside a segment would otherwise close the cue early and corrupt every cue after it.

**`_format_srt` also drops blank segments, and that is a separate defect from the wrapping.** mlx *clears* rather than removes them — "if a segment is instantaneous or does not contain text, clear it" (`transcribe.py`) sets `text` to `""` and then still extends `all_segments` with it. Emitting one produces an SRT block with an index, a timing line and **no text at all**, which is malformed and which strict parsers reject. It is reachable on *any* run, not only under **No verbatim**: the same branch fires whenever `start == end`. The filter sits before `enumerate` so cue numbers stay contiguous — skipping inside the loop would leave gaps in the sequence.

⚠️ **`_wrap_cue` is a no-op for CJK and that is not a bug to be fixed here.** `textwrap` breaks on whitespace, and Japanese and Chinese do not put spaces between words, so a CJK cue is a single token and comes back unchanged (measured: an 88-character Japanese line stays one 88-character line). That is no worse than before the wrapping existed, but it is worth knowing before assuming the feature covers all 100 languages the app advertises. Doing it properly needs character-level breaking against a different width — the convention is ~16 full-width characters, not 42 — so it is a separate feature, not a tweak to this one.

### Model

Direct `mlx_whisper.transcribe()` call with `ASR_MODEL_REPO = "mlx-community/whisper-large-v3-turbo"`. MLX accelerates natively on Apple Silicon. Results are cached via `@st.cache_data(show_spinner=False, max_entries=20)`; the spinner is disabled because per-file progress is rendered by the `st.status` wrapper in `_handle_transcription`.

`_transcribe` also pins `no_speech_threshold=0.6`, `logprob_threshold=-1.0`, and `compression_ratio_threshold=2.4`. These are **mlx_whisper's own defaults**, restated to keep the decode policy visible at the call site — not tuned values. Deleting one is a no-op that lets the library's default track upstream; changing one is a real behavior change, and `test_transcribe_calls_mlx_with_correct_params` asserts all three.

**`_handle_transcription` calls `mx.clear_cache()` in a `finally` around the batch**, and `mlx` is a **declared** dependency because of it (an undeclared direct import breaks the moment `mlx-whisper` stops pulling it in). MLX keeps freed device buffers on a free list rather than returning them, so a finished transcription leaves them resident for the life of the server process. Measured against `whisper-large-v3-turbo` with `word_timestamps=True`: **894 MB** held after an 8-second file and **1.25 GB** after two minutes, all of it reclaimed, for **4.2 ms**. Verified end to end — `peak` reaches 2444 MB during a batch and `mx.get_cache_memory()` reads **0.0 MB** once `_handle_transcription` returns. The next run costs 0.76 s against 0.74 s with the cache warm: it re-allocates rather than reloading, because the **model** lives in `active` memory (a flat **1543 MB** in every measurement) and `clear_cache()` does not touch it.

Three things about it that will otherwise get it reverted:

- ⚠️ **Verify with `mx.get_cache_memory()`, never `top`.** RSS moved **2.6 MB** while 894 MB was reclaimed, because these are device-mapped `MTLBuffer`s. Anyone checking the process's resident size concludes the call does nothing
- **`mx.set_cache_limit()` is the obvious cheaper alternative and is worse** — it caps the free list *during* decode, throttling the run it is meant to help. A batch boundary costs nothing in the middle of the work
- **`finally`, not a plain call after the block.** A tab switch — or any widget — raises `RerunException` mid-batch, and an interrupted run would otherwise hold its buffers until whenever the next transcription finishes, which may be never. `test_handle_transcription_reclaims_the_mlx_cache_when_interrupted` is what pins this, and it is the half that a success-path-only call still passes

Note `import mlx.core as mx` carries **no** `ty` suppression, and it used to. `mlx/core` is a compiled `.so`; `ty` introspects it only through the `mlx/core/*.pyi` stub package the wheel ships beside it (`__init__`, `fast`, `fft`, `linalg`, `metal`, `random`, `distributed`, `cuda` — in the cp312 wheel CI installs as well as the local cp313 one). **Whether a given release carries those stubs is a per-release packaging property, not a version floor.** Checked by installing each: present in 0.31.2 and 0.32.1+, absent in 0.32.0 — the release `5ce3bdb`'s dependency bump landed on, which is why `ea15fec` added `# ty: ignore[unresolved-import]` four days later and an earlier version of this paragraph generalised that one gap into "mlx ships no `.pyi`" (the lock had been on 0.31.2, which `ty` resolves unaided). The 0.32.1 release notes never say "stubs" — the change hides under *Refactor wheel building script (#3818)*, closing ml-explore/mlx#3916 — so bisect by installing rather than by reading notes. The directive is coupled to the locked version in **both** directions: on a stub-less release the bare import is an `unresolved-import` error and needs the line-scoped suppression back (never a `[tool.ty]` rule override, so a genuinely missing import still fails); on a stubbed one a *kept* directive is `unused-ignore-comment`, a warning, and `ty check` exits 1 on warnings — which is what turned the gate red when this upgrade moved the lock to 0.32.2. With the stubs `ty` checks the call for real: `def clear_cache() -> None` in `mlx/core/__init__.pyi`, and a wrong-arity call is an error. Two traps, one recorded in `pyproject.toml`'s `mlx` comment and one in the source comment above the import. The `>=0.24.2` floor in `pyproject.toml` is an `mx.clear_cache()` minimum, not a typing one — `ty` checks whatever `uv.lock` pins. And the comment above the import spells the directive **without** its leading `#`, because `ty` parses a `#`-prefixed `# ty: ignore[...]` anywhere inside a comment as live: mid-line it is reported as an unused suppression (exit 1), and on its own line directly above an import that genuinely fails to resolve it is *applied to that import* — `ty check` passes with exit 0 (measured at 0.0.69 and 0.0.80). That silent half is the real hazard; a bare `ty: ignore[...]` token with no `#` in front is inert. `mlx_whisper` imports it identically; `ty` only checks first-party code, which is why the same statement inside `site-packages` never raised anything.

Model weights are **not** wrapped in `st.cache_resource`. `mlx_whisper` already holds them on a process-level class attribute (`ModelHolder.get_model` in `mlx_whisper/transcribe.py`), so the repo is loaded once per server process; adding `st.cache_resource` would layer a second cache over an existing one.

`_transcribe` is the app's only cache, and it needs no `ttl` or size bound beyond `max_entries=20` — it caches result dicts (text + segments), not media. It stays on `@st.cache_data` rather than `cache_resource`: it returns a nested dict, which is mutable, and `cache_data` hands each caller a fresh unpickled copy, so an edit to one session's result cannot leak into another's. (The two remote-fetch functions that used to sit beside it were `@st.cache_resource` holding raw audio bytes, which is why `tests/test_app.py`'s `_clear_caches` once had to call `st.cache_resource.clear()` as well; see **Testing** for the standing rule if one is ever reintroduced.)

- **Two gaps that used to hide behind that "parse-time only" framing, both now closed.** Stating the limitation as a *rule* invited checking the list rather than the boundary, and both of these are parse-time constructs the rule implied were already covered:
  - **`&` is in the escape class.** `characterReference` is a genuine parse-time micromark construct, so without it `&amp;` / `&#38;` / `&#x26;` decode during parsing — which both breaks the literal display (`Rock &amp; Roll.mp3` showed as `Rock & Roll.mp3`) and, worse, decodes *before* the post-parse text-node passes above, so `clip&#58;streamlit&#58;.mp3` produced a live `:streamlit:` and rendered the logo in `st.subheader`, the `st.status` label, **and** `st.error` alike. `&` is ASCII punctuation, so `\&` is a valid CommonMark characterEscape and suppresses entity parsing outright. Still no injection: entity-decoded characters are never re-tokenized, so `x&#42;bold&#42;.mp3` renders literally and no new link/image syntax can be built this way
  - **Block markers are handled by collapsing whitespace *inside* `_escape_markdown`, not by the character class and not at a call site.** The function's last line is `_MARKDOWN_ESCAPE_RE.sub(r"\\\1", " ".join(text.split()))`. `#`, `>`, `-`, `+`, `|` and ordered-list `N.` / `N)` are deliberately **not** escaped; every block construct needs a *line start*, so removing newlines defeats all of them at once, which is a smaller change than growing the class. **Two** sinks need it, which is why it cannot live at one call site — `isLabel` is what turns on both the automatic `^(\s*)((?:[+\-*]|#+)(?=\s|$)|>)` escape and the `disallowedElements` strip list (`h1`–`h6`, `ul`, `ol`, `li`, `hr`, `blockquote`, `table`), and two renderers do not set it:

    - **`st.subheader`.** This one is genuinely counter-intuitive and an earlier version of this file got it backwards, asserting the heading was "hardened for free". It is not. The heading component does `let [first, ...rest] = body.split("\n")`, renders `first` as `## {first}` with `overrideComponents` — and then renders the remainder with `rest.length > 0 && l(Nt, {source: rest.join("\n"), allowHTML: false})`: a bare `StreamlitMarkdown` with **no `isLabel` and no `disallowedElements`**. So everything after the first newline in a heading is full Markdown, exactly like an alert body. Verified in the 1.61.1 bundle and re-verified at the installed 1.63.0, where the remainder render gained one gate — `!(wrap === false) && rest.length > 0 && StreamlitMarkdown({source: rest.join("\n"), allowHTML: false})` — because 1.63.0 added `wrap: bool = True` (and `icon=`) to `st.subheader`. `wrap=False` drops everything after the first newline but is **not** a substitute for the whitespace collapse in `_escape_markdown`: it is above the `>=1.59` floor, it is frontend-only (the proto still carries the newlines), it also ellipsizes the heading under `white-space: nowrap`, the first line is still rendered without `isLabel`, and `st.error` gained no `wrap` at all.     It *was* reachable at both while the URL tab existed — `_fetch_url_audio` percent-decoded the filename off the URL path, so `%0A` arrived as a real newline and a URL ending `/clip%0A%0A%23%20Big%0A%0A%3E%20quote.mp3` rendered an `<h1>` and a blockquote inside the error box **and** inside the results card. **No *browser* path delivers a newline**: browsers percent-encode LF/CR in a multipart filename before sending it (the HTML spec's "escape a filename" step) and Streamlit's upload route does not decode it, and `st.audio_input` names its own file. A direct PUT to the upload route still can — the route copies `upload.filename` into `UploadedFile.name` unchanged — so the collapse is defence in depth for browser clients and a real guard for anything else. Both tests stay; the cost is one `join`, and the raw name still lands in the transcription dict
- **`$` and `~` are in `_MARKDOWN_ESCAPE_RE` too, and nothing else records why.** The source docstring lists `*`, `_`, backticks, brackets and `:`, and the two bullets above cover `&` and the block markers, so a maintainer trimming the class has no reason on record to keep these two. Streamlit's Markdown is GFM plus math: `$…$` is inline LaTeX rendered through KaTeX (the `st.markdown` docstring: LaTeX expressions "by wrapping them in "$" or "$$""), and the bundled GFM strikethrough matches a *single* tilde as well as a pair (`singleTilde` defaults to true in the 1.63.0 bundle and Streamlit never passes `false`). So `budget $500 vs $700.mp3` would typeset `500 vs` as math and `v1~v2~v3.mp3` would strike `v2` at the heading and the alert, and the `st.status` label's documented subset names Strikethroughs explicitly. Both are parse-time inline constructs, so `\$` and `\~` are ordinary CommonMark character escapes — the same mechanism as the rest of the class. `test_escape_markdown[all_specials]` is the only case that exercises either
- `_display_transcription` renders one stacked section per stored result and nothing else; **the results column's empty state is decided at the call site**, which registers the fragment only when there are results and otherwise renders one `st.container(border=True)` holding `st.caption(EMPTY_RESULTS_HINT, text_alignment="center")`, i.e. `:material/subtitles: Transcripts appear here`. So clicking **Download** with an uncommitted edit serves the *previous* text. Verified end-to-end in real Chrome: typing into the box and clicking once downloaded the pre-edit string; the click's own blur committed the edit and a second click got it. Changing this string means updating `DOWNLOAD_HELP` in `tests/test_app.py` and the README entry with it.

The call sits inside `with results_col:`, and the fragment reruns in place there — measured in Chrome after an edit committed by blur, the edit stuck and every rect in both columns was unchanged. ### Lazy Container Execution

`st.tabs` and `st.expander` can skip computing hidden content via `on_change="rerun"` plus the container's `.open` property, and the general best-practices guidance recommends it for expensive work behind tabs and expanders. This API is present well below the declared `streamlit>=1.59` floor (verified against a 1.58.0 install: `st.tabs` already accepts `key` and `on_change`, and `TabContainer.open` exists). **That guidance does not apply to the Advanced options expander.** Its three widgets are not expensive work — they are widget *declarations* whose return values (`decode_independently`, `time_range_input`, `keyterms`) are consumed unconditionally further down the script. Gating the expander body would leave those names undefined whenever the expander is collapsed, i.e. by default. Widget declarations are cheap; their values are load-bearing. The expander now lives in the sidebar, and that changes nothing here: `st.sidebar` is a plain `DeltaGenerator` with no expandable state, so its widgets run on every script run whether the sidebar is drawn expanded or collapsed (the collapse is client-side), and the **Time range** alert those values feed renders in the main input column above the button it disables, not beside the input — a gated body would take the alert's reason down with the names.

**Nothing in the tab bodies is gated any more, but the tabs still carry `st.tabs(..., on_change="rerun", key="input_tabs")`, and that is deliberate.** The flag exists for the `.open` property, which the source dispatch reads (see the **Transcribe** dispatch bullet under **Input Modes**): without it `TabContainer.open` is `None` on every tab and `_active_sources` degrades to the flat priority chain, i.e. the mis-dispatch bug. `key` exposes the active tab's *label* in session state, which is the only way `AppTest` can switch tabs (it has no tab-selection API), and the fallback-dispatch case depends on it. The gating that this section used to describe — the YouTube and URL tabs guarding their **fetch** on `tab.open` while always declaring the `st.text_input` that fed it, the fetches running below every control and writing back into an `st.container()` slot reserved inside the tab, an `st.skeleton` sized to the player filling that slot while the download ran — went with those tabs. Two lessons from it are worth keeping even with no current caller:

- **Gate the side effect, never the widget.** Wrapping a whole `with tab:` body in `if tab.open:` stops rendering that tab's widgets while it is hidden, and Streamlit removes state for widgets absent from a run (`SessionState._remove_stale_widgets`) — so a typed value would be silently cleared on every tab switch. Widget declarations are cheap and must always run; only the work they trigger gets gated
- **`st.skeleton`'s context-manager form does not redirect bare `st.*` calls into itself** — they land in the *parent* container. Entering the target slot first (`with slot, st.skeleton(...)`) is what keeps the content that replaces the skeleton where the skeleton was. Its testid is `stSkeletonElement`, not `stSkeleton`. And `st.skeleton` is a **1.59.0** API (absent in 1.58.0, bisected directly) — it is why the floor moved off `>=1.58`, and the bundled skill's `performance.md` / `best-practices.md` recommend it without qualification because those docs describe the *installed* Streamlit. **This repo deliberately keeps the installed version and the floor different**, so treat any API the bundled references recommend as needing a floor check before use — `uv run --no-project --with 'streamlit==<floor>' python -c "import inspect, streamlit as st; print(inspect.signature(st.<name>).parameters)"` settles it in one command (check parameters, not just `hasattr` — most of what the 1.63.0 references add is a kwarg on a command that already exists at the floor)

Note that `on_change="rerun"` does not itself skip anything: `TabContainer.__enter__`/`__exit__` are plain passthroughs (Python cannot skip a `with` body), so the flag only enables `.open` tracking and makes tab switches trigger a rerun. Any `if tab.open:` guard is hand-written, and there are currently none.

Two accepted consequences. Switching tabs costs a server rerun. And because a tab switch is a rerun, it can **interrupt an in-flight transcription** — before `on_change="rerun"` tab switching was purely client-side and could not; this is why `_handle_transcription` publishes results progressively rather than once at the end. (A third consequence — that a remote source could not *enable* **Transcribe** from another tab, because it existed only while its own tab was open — went with the remote tabs. Both remaining sources are sticky, so the button's enabled state no longer depends on which tab is showing, only on whether anything is loaded.)

### Accepted formats

Audio: mp3, m4a, wav, opus

Video: mp4, mov, webm, mkv

**The list is short on purpose, and the order is meaningful.** Both tuples run most-likely-first.
`ffmpeg` decodes far more than these eight — the tuples are a *product* decision about what the
uploader advertises and accepts, not a decoder limit.

The forcing constraint is that `st.file_uploader` renders `500MB per file • MP3, M4A, …` inside a
single span styled `white-space: nowrap; overflow: hidden; text-overflow: ellipsis`
(`static/js/FileUploader.*.js`), and no `st.file_uploader` parameter suppresses or reformats it —
the two halves are fed by `max_upload_size` (or `server.maxUploadSize`) and by `type` respectively,
so the only lever on the format list's *length* is shortening `type` itself. Measured
in a running app while it was a single `centered` column: the slot the span fills got **571px**,
the size prefix ate **92px**, leaving **~479px** for the format list at Source Sans 14px (~31–40px
per entry). The former 17-format list needed 546px and truncated mid-word; the current eight need
~265px, so the whole hint is **357px** of text. That budget did not move with the window, because
`centered` caps the main block at 736px (a 704px content box) and the slot is the content width
less a fixed 133px — 12px of dropzone padding each side, the 93px **Upload** button and the 16px gap
between them; 704 − 133 = 571 reproduces the figure.

**The `wide` layout puts the uploader in the left of two equal `st.columns(2, gap="small")`, so
the same fixed deduction — **135px** now, the 133 plus the 1px edge the theme's `showWidgetBorder`
draws on each side of the dropzone (see **Theme**) — comes off a column that scales with the window
instead of stopping at a max-width, and that is a real regression against the fixed column,
accepted rather than fixed.** With the sidebar open the column is `(viewport − 300 − 160 − 16) / 2`
— the sidebar, the main block's 80px padding per side, the column gap — which is 722px at the
user's 1920px viewport and gives the slot **587px**, ~495px for the list: more than before, but
with no floor under it. The slot is 362px at a 1470px viewport, 357 at 1460 and 356 at 1458 — one
short of the text, and the last entry becomes an ellipsis — so the threshold is **~1460px with the
sidebar open** and **~1160px with it collapsed** (fits at 1459 / 1159, truncates at 1458 / 1158;
measured in Chrome via Playwright at each width). The borderless stock dropzone fit down to
1456 / 1156, and the 4px is the theme's 1px border on each side of the dropzone, doubled across
two equal columns; the README already rounded both figures to "about 1460" and "about 1160", so
its numbers did not move. A 13-inch MacBook Air's 1470px viewport fits with 5px to spare; a 1440px
13-inch MacBook Pro shows `…, WEBM…` with the sidebar open — every format is still accepted, only
the label is abbreviated, and collapsing the sidebar restores it. **The gap is what decides the
Air**: at `gap="medium"` (32px) each column loses 8px and the slot at 1470 is 356px (354 under
the theme's border), 1px short, which is why the wider gutter was tried and reverted. Two other levers were weighed and rejected:
dropping `mkv` (325px, fits 1440 but not 1366) narrows the accepted-upload surface as a side
effect of a layout change, and a `[3, 2]` split (threshold ~1300px) leaves the input column
mostly empty on the display the layout was built for. `test_format_list_fits_the_dropzone_hint`
guards the list's *length* with a 60-character proxy for the `centered` budget, and the ceiling
stayed there through the move on purpose — the 1920px figure has no floor under it, so ~479px is
the only budget that still means something. Read it for what it checks — that the list is not
lengthened — not as a fit guarantee: the test is green at every viewport, and nothing checks the
viewport half.

Two rejected alternatives, both worth not re-deriving:

- **An `st.caption` restating the full list below the uploader.** Works, but adds a permanent line
  of chrome under the dropzone to compensate for a truncated label. Rejected on UI grounds
- **Shortening `type` to the MIME shortcuts (`type=["audio", "video"]`).** Renders as just
  `audio, video` — the frontend formatter strips the `/*` and skips the uppercasing it applies to
  bare extensions — and always fits. But `enforce_filename_restriction`
  (`streamlit/elements/lib/file_uploader_utils.py`) **skips server-side validation entirely** when
  any entry contains a `/`, because the backend can't tell whether a file was meant to match a
  MIME pattern or an extension. Bare extensions are what keep that bypass guard active

Dropping a format rejects it browser-side *and* server-side, so this is a real narrowing, not a
label tweak — and since the remote tabs went, the uploader is the only *tab* that consults these
tuples, so they are the whole accepted-*upload* surface. The Record tab's `st.audio_input` delivers
WAV without touching them; dropping `wav` here would not stop a recording. (`MEDIA_MIME_TYPES`
mirrors the uploader's *normalized* accept list, which adds `.mpeg4` to these eight; see the
`st.audio` bullet under **Input Modes**.)

Formats removed when the list was cut to eight, in case one needs restoring: `aac` (near-redundant
— standalone `.aac` is rare, AAC audio almost always arrives inside `.m4a`), `flac`, `ogg`
(Telegram voice notes, where WhatsApp uses `.opus`), `aiff`, `avi`, `wmv`, `flv`, `mpeg`, `3gpp`.

If a newline ever seems like the fix for a long format string somewhere: Streamlit's markdown
pipeline ships no `remark-breaks`, so a single `\n` collapses to a space rather than breaking.

### Upload Limit

- Per-file cap of **500 MB**, set in `.streamlit/config.toml` via `server.maxUploadSize`
- Enforced browser-side *and* server-side — the upload route rejects an oversized body three ways (a `Content-Length` fast-fail, a cap on the streaming read, and an exact post-parse size check), all HTTP 413, so the cap is not client-bypassable. Each file is a separate PUT, so with `accept_multiple_files=True` the cap is per-file, not aggregate
- Server restart required after changing this setting

### Theme

- **A macOS-native custom theme in `.streamlit/config.toml` — colours only, both modes defined.** Dark: Apple's system greys for the surfaces (`#1C1C1E` page, `#2C2C2E` wells — the dropzone, the text area, the selectbox), `#DDDDDD` text (white at 85% over the page, macOS `labelColor`), the macOS dark-mode accent `#0A84FF` as `primaryColor`, `#48484A` hairline borders and systemRed `#FF453A` as `redColor`. Light: white page, `#F2F2F7` wells (Apple's grouped background), `#141416` text, `#0061C2` primary (apple.com's button blue — the system `#007AFF` puts a white label at 4.0:1), `#AEAEB2` borders and `#D70015` (Apple's increase-contrast red; the standard `#FF3B30` is 3.6:1 on white). No sidebar sections: Streamlit already swaps the two backgrounds in the sidebar, which *is* the source-list look. The thesis is the app's own — it cannot run anywhere but a Mac, its caption promises everything happens locally on your Mac, and it is already shaped like a macOS window (a Settings source list, a content pane, one default action)
- **The functional reason is the go/fail collision, and it is not taste.** Stock Streamlit's `primaryColor` is `#ff4b4b` — the same red as `st.error` — so **Transcribe**, the active tab, the selected **Transcript format** and an on toggle all rendered in the failure colour, and `Translate to English` switched on sat directly above a red alert in the same hue. ### Error Handling

- `RuntimeError` caught explicitly for transcription failures
- Unexpected exceptions shown with `st.exception()`
- **Nothing calls `st.error` directly — every error goes through `_error(message)`**, which applies `ERROR_ICON`, condenses, and escapes. All three are structural on purpose:
  - **The icon.** `st.error` has no default — its docstring is explicit that "if no leading icon is found, no icon is displayed", and the leading-emoji extraction it *does* perform never fires here because every body starts with a word. So an omission is a real visual difference, not a no-op. It used to be a literal repeated at seven call sites with six of them missing it; a helper makes a new bare-box `st.error` impossible rather than merely documented-against. There are two call sites left (the per-file failure replay in `_handle_transcription` and the **Time range** validation error) — seven at introduction, six once `_handle_transcription`'s two inline failure branches folded into the single replay-loop call, two now that the four remote-tab sites are gone — and the helper is kept at two for the same reason it was introduced at seven. **The same "no default icon" rule applies to `st.info`**, which now has no call site at all (its one use was the URL tab's YouTube-link redirect, which passed `:material/smart_display:` explicitly). If one appears, pass an icon; if a second appears, add an `_info` helper rather than repeating the literal, since that is precisely how `st.error` drifted to six bare boxes
  - **The escaping, and this is the part that is not cosmetic.** `st.error`'s body is one of the two sinks that render without the frontend's `isLabel` flag (see `_escape_markdown`), and **two untrusted inputs reach it verbatim**: the upload's raw filename, which `_handle_transcription` interpolates into both failure messages (`f"Transcription failed for {uploaded_file.name}: {e}"`), and the raw **Time range** text, which `_validate_time_range` echoes back (`f"Invalid time range: {token!r} …"`). an unescaped `![](…)` in either fires an image request to whatever destination the text spells — the **Time range** text is free-form and can carry a full URL, and a filename needs no `/` to point off-site because `https:host` resolves as `https://host/`. (While the remote tabs existed the exception text itself was untrusted too: `yt-dlp`'s `UnsupportedError` is literally `f"Unsupported URL: {url}"`, and `HTTPError.__str__` embeds a server-controlled reason phrase. Escaping the *whole* message rather than the filename span is what made that a non-event, and it is why the whole-message rule stays even though the library text reaching `_error` today is `mlx_whisper`'s and ffmpeg's)
  - **The length cap, which exists because the visibility fix created the need for it.** `_condense` collapses the message to one line and caps it at `ERROR_MESSAGE_LIMIT = 240`, keeping the **head and the tail** rather than truncating. The exception text was never written for a UI: a corrupt file makes `mlx_whisper` raise `RuntimeError("Failed to load audio: " + ffmpeg's entire stderr)` — measured at **1740 characters over 14 lines**, of which roughly 1500 are ffmpeg's version banner and its `--enable-*` configure flags. That cost nothing while per-file errors rendered into a collapsed `st.status` nobody had reason to open; making them visible is what promoted it from invisible to a wall of text, so it is a consequence of that fix rather than a pre-existing wart. Both ends are kept because the two useful halves sit at opposite ends — the head carries `Transcription failed for <name>: Failed to load audio:` (what failed), the tail carries `Invalid data found when processing input` (why). Head-only renders the version banner; tail-only drops the filename and the operation. 240 was chosen by rendering 240/320/400 against the real failure, not picked
  - **`_condense` runs *before* `_escape_markdown`, and the order is load-bearing.** Escaping first would let the cut land between a backslash and the character it escapes, dropping the backslash into the head and releasing a live `[` or `:` into the tail. `test_error_condenses_before_escaping` pins it, and the observable signature is the ellipsis marker itself: inserted before escaping it renders escaped, inserted after it arrives raw — no boundary arithmetic required. A first draft of that test computed the cut's parity to land a backslash exactly on the boundary, which was fragile and unnecessary
  - `_error` escapes the **whole** message rather than the untrusted spans, so callers pass raw text and never escape at the interpolation site — which is what makes "no unescaped interpolation" checkable by grepping for `st.error(`. Escaping the fixed literals too is harmless: `:` becomes `\:`, which renders as a colon. The cost is that every exact-match assertion on an `_error` message in `tests/test_app.py` carries `\:` in its expected string
  - **Where the two call sites render is a layout decision, and both halves are pinned.** The **Time range** alert renders in the main **input column**, directly above the Transcribe button, while the `st.text_input` that produced it sits in the sidebar under the collapsed-by-default Advanced options expander: the alert belongs with the button it disables, not with the input, so a disabled **Transcribe** always shows its reason in the same column. (It used to render outside the expander *and* outside the bordered controls card, above the button, while every control lived in the main column — the sidebar move is what turned "outside the card" into "in a different column from the input".) `test_time_range_error_renders_beside_the_transcribe_button` pins it — `input_col.error` carries `_validate_time_range("90,30")` while `at.sidebar.error` and `results_col.error` are empty — and moving the `_error` call into the sidebar fails it and nothing else. The per-file failure replay renders in the **results column**, because `_handle_transcription` is called inside `with results_col:`, so the alerts land under the `st.status` they belong to; for an all-failed batch that is the *end* of the column on the click run, since the call site renders the hint only `elif not batch_just_ran` (a first draft rendered `Transcripts appear here` under the failure alert; a second left the column blank on every later run — see the `_display_transcription` bullet). `test_transcription_failure_renders_an_escaped_alert` reads `results_col.error` rather than the unscoped `at.error` and asserts `results_col.caption == []`, and `test_transcription_status_renders_in_the_results_column` pins the status beside it; hoisting the `_handle_transcription` call out of `with results_col:` fails both (measured)
